## 一、项目概述

### 1.1 项目名称
**鲲鹏记账**（KunPengBook）

### 1.2 产品定位
一款面向个人用户的跨平台（Windows / macOS）桌面记账应用。以简洁、直观的操作帮助用户记录日常开销，并通过二级分类体系清晰掌握资金流向。

### 1.3 目标用户
- 无编程背景的普通个人用户
- 希望简单记录日常收支、分析消费习惯的人群
- 需要离线使用、数据本地存储、注重隐私的用户

### 1.4 核心目标
1. **记录花销**：支持快速录入每笔支出的金额、日期、备注，并选择一级大类和二级小类。
2. **二级分类体系**：提供预设的分类树（一级 + 二级），方便用户归类。
3. **数据持久化**：所有数据保存在本地，无需联网，保障隐私。
4. **跨平台运行**：同一个应用可在 Windows 和 macOS 上运行，且界面风格原生。
5. **数据查看与管理**：支持列表查看、按日期/分类筛选、编辑/删除记录，并能统计汇总。

## 三、技术栈选型方案

由于您是技术小白，我将提供**三种主流跨平台桌面开发方案**，并对比各自优劣，由您最终决定。所有方案均可实现上述功能，并且都能运行在 Windows 和 macOS 上。

### 方案 A：Electron + Vue/React（Web 技术栈）

**技术组合**：  
- 前端框架：Vue 3 或 React 18  
- UI 组件库：Element Plus 或 Ant Design  
- 数据存储：SQLite（通过 `better-sqlite3` 或 `knex`）  
- 打包工具：Electron Builder  

**优点**：
- 开发速度快，生态丰富，社区活跃，有海量现成组件。
- 界面可做到非常美观，易于实现图表统计（如 ECharts）。
- 单套代码同时构建 Windows 和 macOS 安装包。
- 升级维护方便，后续可扩展为 Web 版或移动端（复用大部分代码）。

**缺点**：
- 应用体积较大（包含 Chromium 内核），约 60~100MB。
- 内存占用相对较高（但对于记账应用影响不大）。
- 启动速度略慢于原生应用。

**适用场景**：您希望界面精美、开发快捷，且不介意安装包体积。

---

### 方案 B：Flutter（Google 跨平台框架）

**技术组合**：  
- 框架：Flutter 3.x + Dart  
- UI 库：Material Design 或 Cupertino（原生风格）  
- 数据存储：SQLite（sqflite） 或 Hive（NoSQL）  
- 打包工具：Flutter 官方构建工具  

**优点**：
- 性能接近原生，渲染效率高，60fps 流畅。
- 开发效率高，热重载方便调试。
- 生成的安装包体积适中（约 20~40MB）。
- 界面可同时适配 Windows 和 macOS，且视觉风格贴近各平台原生。

**缺点**：
- 生态相对于 Web 稍小，部分 UI 组件需要自己封装。
- 学习曲线略陡（但您无需学习，由我们开发）。
- 图表库相对较少，但常用图表可以实现。

**适用场景**：您更看重性能和接近原生的体验，且希望应用较为轻量。

---

### 方案 C：.NET MAUI（微软跨平台方案）

**技术组合**：  
- 框架：.NET 8 + MAUI (Multi-platform App UI)  
- 语言：C#  
- UI：XAML 或 C# 标记  
- 数据存储：SQLite（SQLite-net）  
- 打包：Visual Studio 构建工具  

**优点**：
- 微软官方支持，可调用大量 .NET 类库。
- 性能不错，与 Flutter 相近。
- 对 Windows 原生支持最好，macOS 也完全支持。
- 适合有 .NET 背景的开发者（但您不关心）。

**缺点**：
- 生态和社区规模远小于 Electron 和 Flutter。
- 开发工具对非 Windows 用户可能不够友好（但我们可以解决）。
- 国内资料较少，遇到问题解决成本稍高。

**适用场景**：您偏好微软技术栈，或者未来有整合 .NET 生态的需求。

---

# 鲲鹏记账 —— Git 版本管理初始化方案

> **目标**：为“鲲鹏记账”项目建立 Git 版本管理，确保代码安全、可回溯、防丢失。

## 二、需求背景
“鲲鹏记账”项目正在开发中，所有代码和配置文件仅存在于本地电脑。一旦硬盘损坏、误删除或修改出错，将无法找回。您需要一套可靠的版本管理机制，来：
- **保存每个阶段的代码快照**，可随时回退到任意历史版本。
- **记录修改日志**，清楚知道每次改动的内容和原因。

## 四、操作方案（将向您解释并征求同意）

### 步骤 1：初始化仓库（`git init`）
- **操作**：在项目根目录执行 `git init`，生成隐藏的 `.git` 文件夹。
- **效果**：从此该目录下的所有修改都会被 Git 跟踪。
- **风险**：无风险。.git 文件夹不占空间，可随时删除恢复原状。

### 步骤 2：创建 `.gitignore` 文件
- **操作**：编写 `.gitignore`，指定忽略以下内容：
  - `node_modules/`、`build/`、`dist/`、`*.log`、`*.tmp`
  - 操作系统垃圾文件（如 `.DS_Store`、`Thumbs.db`）
  - IDE 配置文件（如 `.vscode/`、`.idea/`）
  - 打包产物（如 `release/`、`*.exe`、`*.dmg` 等）
- **效果**：防止将大文件和编译结果存入 Git，避免仓库臃肿。
- **风险**：请确认是否有需要保留的配置文件（如 `.env`），默认会忽略 `*.env`，如项目中有环境变量示例文件，我们可单独处理。

### 步骤 3：暂存所有文件（`git add .`）
- **操作**：将当前所有未忽略的文件加入“暂存区”，准备提交。
- **效果**：Git 将对这些文件生成快照。
- **风险**：若 `.gitignore` 配置不当，可能误提交大文件。我会先展示忽略列表，由您确认后再执行。

### 步骤 4：创建首次提交（`git commit -m "初始提交：鲲鹏记账 v1.0"`）
- **操作**：将暂存区内容永久保存为一个版本（commit），附带说明。
- **效果**：您有了第一个可回退的版本。
- **风险**：无，提交不会丢失任何代码。

### 步骤 5（可选）：建立分支 `develop`
- **操作**：创建独立开发分支，保持 `main` 分支始终稳定。
- **效果**：新功能可大胆尝试，出错时直接丢弃分支，不影响主版本。
- **风险**：稍显复杂，但可教您如何切换分支。

## 五、日常使用简要说明（征得同意后另建文档）
- **“提交”保存一次改动**：每次完成一个功能或修复后，执行 `git add .` + `git commit -m "描述"`。
- **查看历史**：执行 `git log --oneline` 查看所有版本号。
- **回退到某版本**：执行 `git reset --hard <版本号>`（可恢复，但需谨慎）。
