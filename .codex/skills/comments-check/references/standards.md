# 注释检查判据、示例与报告模板

本文件是 comments-check 技能的详细参考：给出三项检查的可操作判据、好坏注释示例与报告模板。

## 目录

1. 检查一：注释覆盖率（3:7 原则）判据
2. 检查二：注释与代码匹配判据
3. 检查三：小白视角判据
4. 好注释 / 坏注释对比示例
5. 报告模板

## 1. 检查一：注释覆盖率（3:7 原则）

### 达标定义

- 每个函数/方法上方或行内有注释，说明：**做什么、为什么存在、关键参数与返回值**。
- 重要核心代码段有注释：业务逻辑、算法、正则、边界处理、IPC 消息、SQL、金额与日期处理。
- 数量目标：非空行中约 30% 为注释（10 行代码 ≈ 3 行注释），允许 20%–40% 弹性区间。

### 什么算“有效注释”

有效注释必须新增信息，至少满足以下之一：

- 解释“为什么这样写”（例如：`// 用 WAL 模式：读写并发更好，崩溃恢复更安全`）
- 解释“做什么”的高层意图（例如：`// 压缩+合并一行，相邻相同块只合并一次`）
- 说明边界与例外（例如：`// 满盘时不生成新块，原样返回`）

### 什么算“无效注释”（不计入，也不能代替有效注释）

- 复述代码：`i++ // i 加一`
- 占位：`// TODO 待补充`、`// fixme`
- 过时残留的注释（同时违反检查二）

## 2. 检查二：注释与代码匹配判据

逐条核对注释中的“事实性声明”：

- 方向/顺序：注释说“左移/右移”“升序/降序”，代码是否一致？
- 边界：注释说“满盘原样返回”“空列表返回 0”，代码是否一致？
- 返回值与副作用：注释说的返回值类型、是否修改入参，与代码是否一致？
- 数值与符号：注释说“得分 +4”“90% 出 2”，代码中的常量是否一致？

判定结论：

- 一致 → 通过。
- 不一致但代码正确 → 修改注释（🔴 误导读者）。
- 注释正确但代码有 bug → 报告给用户，不擅自改业务逻辑。

## 3. 检查三：小白视角判据

对每个注释问三个问题：

1. 非技术读者能看懂“这段代码解决什么问题”吗？
2. 专业名词/缩写是否首次出现就给了一句通俗解释？
3. 注释是在解释“为什么”，还是只复述“做了什么”？

常见专业名词的通俗写法示例：

| 名词 | 通俗解释示例 |
| --- | --- |
| 深拷贝 | 复制一份全新的数据，改副本不影响原件 |
| WAL 日志模式 | 先把改动写进日志再落盘，程序崩溃时数据更容易恢复 |
| 防抖 debounce | 用户连续操作时只执行最后一次，避免频繁触发 |
| IPC 通信 | 界面和后台主进程之间传话的通道 |
| JOIN 联表查询 | 把两张表按共同字段拼成一张大表来查 |
| AUTOINCREMENT 自增 | 每插入一行自动生成一个不重复的编号 |

## 4. 好注释 / 坏注释对比示例

### 例 1：同一函数的两种注释

坏（只有“做什么”，没有“为什么”，专业读者才懂）：

```js
// 移动一行并合并
function mergeLine(line) {
  const compact = line.filter((v) => v !== 0) // 去 0
  ...
}
```

好（解释意图、规则与边界）：

```js
/**
 * 把一行方块“压缩 + 合并”：去掉所有空格，相邻相同的值只合并一次。
 * 例如 [2,2,2,2] 会变成 [4,4,0,0] 而不是 [8,0,0,0]，
 * 因为 2048 规则里同一轮不能连锁合并。
 * @returns {{line: number[], gained: number}} 合并后的行与新增分数
 */
function mergeLine(line) { ... }
```

### 例 2：专业名词加解释

坏：`// 启用 WAL`

好：`// 启用 WAL 日志模式：写操作先记日志再落盘，读写并发更好，程序崩溃时数据也更安全`

### 例 3：注释与代码不匹配（🔴）

```js
// 左移：把两个 2 合并到最右侧
const res = move(grid, DIR.LEFT)
```

代码实际是左移，注释却说“合并到最右侧”，与代码矛盾，会误导读者，必须修正注释。

```markdown
## 缺少注释的函数

| 文件 | 行号 | 函数 | 建议补充的注释要点 |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## 注释与代码不匹配（🔴）

| 文件 | 行号 | 注释原文 | 代码实际行为 | 修复建议 |
| --- | --- | --- | --- | --- |

## 小白视角问题（🟡）

| 文件 | 行号 | 术语/表达 | 建议的通俗写法 |
| --- | --- | --- | --- |

## 综合评价

按严重程度排序的改进清单。
```
