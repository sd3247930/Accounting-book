# 注释检查

## 概览

对项目代码执行三项注释检查并输出中文报告：

1. **注释覆盖率**：函数与重要核心代码是否缺少注释；整体目标约 10 行代码中有 3 行注释（30%）。
2. **注释与代码匹配**：注释描述是否与实际逻辑一致，是否误导读者。
3. **小白视角**：注释是否通俗易懂，非技术背景的读者能否看懂“这段代码在做什么、为什么”。

机械统计交给 `scripts/check_comments.py`，语义判断由 Codex 阅读代码完成。

## 工作流程

1. **确定范围**：使用用户指定的文件/目录；未指定时默认扫描 `src/`、`electron/`、`shared/`，排除 `node_modules/`、`dist/`、`release/`、`packages/`、`.git/` 等构建产物与第三方代码。
2. **机械统计**：运行 `python scripts/check_comments.py <路径...>`，得到每个文件的注释比例、函数总数、缺少前置注释的函数清单（含行号）。
3. **语义检查**：逐文件阅读核心代码，按下方“检查标准”逐项判断；不要只依赖脚本结果。
4. **输出报告**：在项目根目录生成 `comments-report.md`（中文、表格），结构见“报告格式”。

## 检查标准

### 1. 注释覆盖率（3:7 原则）

- 每个函数/方法必须有注释，说明“做什么、为什么存在、关键参数与返回值”。
- 重要核心代码段必须有注释：业务逻辑、算法、正则、边界处理、IPC 消息、SQL 语句、金额/日期等关键字段处理。
- 数量目标：非空行中约 30% 为注释（10 行代码 ≈ 3 行注释），允许 20%–40% 的弹性区间。
- 无效注释不计入：如 `i++ // i 加一` 这类复述代码、无信息量的占位注释。
- 样板代码（import/require、组件 props 声明等）可低于下限，但不代表函数可以没有注释。

### 2. 注释与代码匹配

- 注释描述的行为必须与实际逻辑一致：算法步骤、边界条件、返回值、副作用、方向与符号（如“左移/右移”“升序/降序”“加/减”）。
- 注释与代码不一致属于 🔴 严重问题（会误导读者）；修复方式是修正注释，若确认是代码 bug 则报告给用户决定是否改代码。

### 3. 小白视角

- 面向不懂技术的读者，解释“是什么、为什么、怎么用”，避免只堆专业缩写。
- 首次出现的专业名词（如“防抖”“WAL 日志模式”“深拷贝”“IPC 通信”）给一句通俗解释或类比。
- 好注释能回答：“这段代码解决什么问题？为什么这样写？”而不是复述代码本身。

详细判据、好坏示例与报告模板见 `references/standards.md`。

## 报告格式

`comments-report.md`（中文、表格、非技术用户可读）：

| 章节 | 内容 |
| --- | --- |
| 概览 | 检查范围、文件数、整体评分（A/B/C/D） |
| 注释覆盖率 | 每个文件的代码行/注释行/比例/达标状态表格 |
| 缺少注释的函数 | 函数名 + 文件 + 行号 + 建议补充的注释要点 |
| 注释与代码不匹配 | 文件 + 行号 + 注释原文 + 实际行为 + 修复建议（🔴） |
| 小白视角问题 | 文件 + 行号 + 术语/表达 + 建议的通俗写法（🟡） |
| 综合评价 | 按严重程度排序的改进清单 |

## 评分

- **A**：三项标准全部达标，无明显问题。
- **B**：个别文件注释偏少或略技术化，不涉及误导。
- **C**：多个文件缺少关键注释，或存在少量注释与代码不匹配。
- **D**：大面积缺注释，或注释严重误导读者。
